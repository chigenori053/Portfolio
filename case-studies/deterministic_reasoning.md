# ケーススタディ: Deterministic Reasoning — 非決定的推論への対応設計

## 概要

AI推論システムの多くは、同じ入力に対して異なる出力を返しうる。監査・規制・安全性が関わる領域でAIを使うには、この非決定性を「仕方がないもの」として受け入れるのではなく、**どこで、どの程度の非決定性が残るかを構造的に管理する**必要がある。本ケーススタディは、この課題に対する設計を横断的に整理する。

## 問題設定 — 非決定的推論に対する立場

LLMを使ったワークフローの構造的弱点は次の3点に集約できる。

1. 同じ入力でも実行結果が変わり、再現性がなく検証もデバッグもできない
2. なぜその結論に至ったかが残らず、事後に監査できない
3. 失敗したときに安全に戻せる単位が定義されていない

この3点に対し、[ReasonScript](../projects/reasonscript.md)・[Design_BrainModel](../projects/design_brainmodel.md)・[MRA](../projects/mra.md) がそれぞれ異なる角度から対応している。

## State / Evidence / Provenance

推論の状態変更を「誰が、いつ、何を根拠に行ったか」まで含めて扱う設計が、系譜全体で繰り返し現れる。

| プロジェクト | State(状態) | Evidence/根拠 | Provenance(来歴) |
|---|---|---|---|
| ReasonScript | `State`(`apply`でのみ書き込み、`rollback`でのみ復元) | `Proof`(不変条件、`invalid`を含めば自動ロールバック) | ExecutionPlanの生成履歴 |
| COHERENT | `AcceptStore`/`ReviewStore`/`RejectStore` | `DecisionLog`(判定に必ず添付) | `ProcessingResult`のAction+Log |
| LanguageModel(MRA) | Molecular Memoryの正規状態 | Evidence(主張を支持/反証する参照可能な根拠) | Provenance(入力・抽出器・モデル・時刻・変換履歴) |
| VisionWorldModel | 分子構造の世代(`water@generation-1`など) | グラフ検証を通過した候補のみ | ハッシュで連結された判断(Decision)の履歴 |

## apply / rollback による状態変更制御

ReasonScript は、状態を書き込む操作を `apply` の1つに、復元する操作を `rollback` の1つに限定している。`Proof` の内部文字列に `invalid` が含まれる場合、決定論的な証明失敗として扱われ、直前の安全な `State` チェックポイントへの自動ロールバックが起動する。

「推論が失敗したときにどこまで戻るか」を後付けのエラーハンドリングではなく、**言語の意味論そのものに組み込んだ**設計であり、状態を触れる操作を2つに限定することでロールバック安全性を言語レベルで成立させている。

## Canonicalization

Design_BrainModel は、決定論の実現手段を仕様レベルで凍結している。

| 項目 | 固定値 |
|---|---|
| ハッシュアルゴリズム | FNV-1a 64bit |
| シード | `0xcbf29ce484222325` |
| 浮動小数点の整形 | `{:.6}` の固定精度文字列 |
| リスト型フィールド | ハッシュ前にソート |
| `Option`の符号化 | `null` または `some:<value>` |
| 空文字列と`None` | 区別する |

浮動小数点の丸め方や空文字列の扱いまで仕様に書くことで、実装者の裁量が入る余地を潰し、「たまたま今は一致している」状態を排除している。決定論ゲートは、同一入力に対して `snapshot_v2` のハッシュ・テンプレート選択・説明テキストが完全一致することを要求する。

## Golden Artifacts

ReasonScript の `golden/` コーパスは、ソースコードから中間表現への変換結果を期待値と比較することで、コンパイルパイプラインの変更が既存の意味論を壊していないかを機械的に検証する。CI(`./reason ci`)に組み込まれており、2026-08-12の実行で全ステージPASS・1,116件のテスト通過を確認している。

## 実用上の制約

非決定性への対応は万能ではない。

- **GPU等による残存非決定性**: LanguageModel の再現性要件は「同一のモデル・ベクトル辞書・メモリスナップショット・検索設定・乱数seed・入力に対する候補順位と検証結果は再現可能でなければならない」としつつ、「GPU等による非決定性が残る場合は、その範囲と許容差を記録する」と現実的な基準を置いている。非決定性を「ないことにする」のではなく、残る場合は範囲を記録するという方針である
- **設計確認と性能実測の混同を避ける**: COHERENT の記憶再利用機構は「θ掃引で意図どおりの挙動をする」ことは確認できているが、これは決定論的に動作を確認できたという設計確認であり、実ワークロードでの効果(性能)としては別問題として扱う必要がある。この区別を怠ると、動作の正しさと効果の大きさを混同した過大な主張につながる(実例は[AI支援開発の責任分界](../methodology/ai_assisted_development.md)を参照)
- **推論爆発への対応は道半ば**: Design_BrainModel v1は、決定論ゲート自体は機能していたが、探索空間の非線形な増加(推論爆発)を止める根拠のある機構を持たないまま強引に抑制していた。「決定論的であること」と「安定して収束すること」は別の性質であり、前者を保証しても後者が自動的に保証されるわけではない、という限界が明らかになった

## 得られた知見

- 決定論は「言語仕様として保証する部分」(ExecutionPlan生成、ロールバック)と、「運用として範囲を記録する部分」(GPU非決定性)を分けて設計する必要がある
- Evidence/Provenanceを構造として持たせることで、「なぜその判断に至ったか」を後から機械的に追跡できるようになる。この設計は、実装コストを増やす代わりに監査可能性を得るというトレードオフである
- 決定論ゲート(ハッシュ完全一致)は「同じ入力から同じ出力が出ること」を保証するが、「出力が意図どおり収束すること」は別途保証する必要がある。Design_BrainModel v1の推論爆発は、この2つを混同しないための実例として学びが大きい
