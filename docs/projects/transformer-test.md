# RS-DT-JP-GREET-001（Transformer_Test）

> **ReasonScript の構造制約を Transformer に適用し、決定論的・観測可能・構造制約付きの
> ニューラルネットワークが学習効率を改善するかを検証する実験。**
> ReasonScript にとっては**外部検証** — 「言語仕様として定義した決定論・観測可能性が、
> 自作の CI 以外の現実的なワークロード（ニューラルネットワークの学習）でも成立するか」を、
> ReasonScript の外部から確かめるプロジェクトです。

## 何を検証しようとしたプロジェクトか

ReasonScript は「推論は決定論的に、検証可能に記述できる」という仕様を持つ言語です。
しかし、その仕様が自作の CI（1,116テスト）以外の場所——特に、非決定性の温床になりやすい
**ニューラルネットワークの学習**というワークロード——でも成り立つのかは、ReasonScript
自身のリポジトリだけでは確かめられません。

RS-DT-JP-GREET-001 は、ReasonScript の`.rsn`だけで Transformer を実装し、日本語の
挨拶8クラス分類というタスクに実際に学習させることで、この問いに答えようとした実験です。
言語の正規層（学習・推論のロジック）は ReasonScript、データ前処理などのホスト適応層は
Python、ダイジェストの独立再計算は Rust という3層構成を取り、**「本当に決定論的か」を
Python 実装とは独立した Rust の再計算でも検証する**設計になっています。

Model A〜D の4段階で構造制約を積み増していく設計です。

| モデル | 内容 |
|---|---|
| Model A | ベースライン Transformer（2層2ヘッド） |
| Model B | Model A と同一構成・決定論のみ検証（seed 注入で A/B の違いを作る） |
| Model C | Reason Relation Matrix によるアテンションバイアスを追加 |
| Model D | 疎ルーティング（top-K 選択、非選択エッジは計算自体を除外）を追加 |

## 現時点で達成できたこと（実測）

机上検討ではなく、**実際に `reason run` で実行し数値を確認した事実**として記録されているものです。

- **ReasonScript から Transformer が実際に学習する** — 2層2ヘッドの Transformer
  （埋め込み・Pre-LayerNorm・残差・交差エントロピー・Adam）を `.rsn` のみで実装し、
  loss の単調減少を確認（例: 16.71 → 0.003、100 step）。
- **決定論が成立する** — 同一 seed で2回学習し、パラメータチェックポイント（`.rstensor`）の
  SHA-256 が**完全一致**（`BIT_IDENTICAL`）。
- **観測が計算に影響しない** — `tensor.save` による中間値（活性・Q/K/V・勾配）のエクスポートを
  入れても、最終出力が変わらないことを確認。
- **構造バイアスと疎ルーティングが機能する** — Model C（Reason Relation Matrix による
  アテンションバイアス）・Model D（疎ルーティング）ともに学習が進行。Model D の
  `available/selected/disabled` ルーティング記録も過不足なく機能することを確認。
- **独立実装による相互検証** — Rust 製の独立検証ツール（`verify/`）が、`.rstensor` の
  チェックサムとディレクトリダイジェストの両方で、Python 側の実装と完全一致する値を算出。
- **実データでの学習・評価** — 実際の日本語挨拶データセット（8クラス、Train/Validation/
  Test A/B/C を完全分離、全ペア間で verbatim overlap = 0 を検証済み）で Model A を学習し、
  Test A 97.9% / Test B 95.8% / Test C 89.6%（size=96、100 step）を達成。
- **介入テストが動作する** — ノードへの zero 介入による before/after の確率比較が機能。
- **基盤側の不具合を3件発見・修正** — 実験の実装過程で ReasonScript v0.5.4.8 の型検査バグを
  3件発見し、v0.5.4.9 で修正。うち1件（L-006）は「`/` 演算子が Int 同士でも実行時は Float を
  返すが静的型は Int のままだった」という、**型エラーが出ないまま値が壊れる**種類の不具合で、
  発見しにくいものだった。修正はいずれも静的型検査ロジックのみで、修正前後で self-check の
  loss curve が完全一致することを実測確認し、実行時の挙動が変わっていないことを確かめている。

## 現時点で達成できなかったこと

- **本実験（Phase 7〜9）は未実施** — Model A〜D を比較する本来のアブレーション実験・
  最終検証は着手していない。Phase 1 のスモークランで**天井効果**（Model A 単体でも
  短時間でほぼ精度が飽和し、Model C/D が示せる改善幅がほぼ残らない）が実測され、
  Test B / Test C（特に Test C）を主指標とする方針に切り替えた上で、Phase 4〜9 の
  実行基盤（run-matrix ドライバ）を実装しパイロット実験を開始したが、後述の性能制約により
  **一時中断**した。
- **フル実験マトリクスは現実的な時間で回らない** — 想定していた7データサイズ×5 seed×
  6モデル構成 ≈ 295本のフルマトリクスは、Model C/D が使う Reason Relation Matrix の
  評価コストが高く（1例あたり約2.5〜3秒の追加コスト）、現状の実装のままでは合計数十時間
  規模になることが判明した。原因は ReasonScript が**バイトコンパイルなしの木構造
  インタプリタ**であることに起因する部分（変更不可）と、本プロジェクト側の実装非効率
  （`if` 15個の独立連鎖。`elif` 化で約3倍高速化できることを実測済みだが未適用）の
  両方が絡んでいる。
- **D3（無作為ルーティング対照）は未実装** — 疎ルーティングの優位性を正しく主張するために
  必要な対照群だが、`model_d.rsn` にホスト供給インデックスを受け付ける関数がまだない。
- **未修正の言語仕様上の制約が残る** — `tensor.grad` の対象を明示的に `tensor.parameter(...)`
  で包む必要がある、式を演算子の前で改行できない、Int→Float の暗黙キャストが存在しない、
  型注釈のない引数が `Unknown` 型になり `if` 条件に使えない、`tensor.to_array(...)` の結果に
  直接添字アクセスできない、という5件の言語仕様上の制約（L-002〜L-008の一部）が
  `docs/limitations.md` に記録されており、いずれも回避策はあるが言語側の修正はされていない。
- **Runtime の Rust 化はスコープ外と判断** — 性能制約の根本解決として Tensor 演算・自動微分・
  optimizer を Rust に再実装する案を検討したが、①基盤は読み取り専用という本プロジェクトの
  絶対条件、②基盤は他プロジェクト（LanguageModel 等）とも共有されるリソースであること、
  ③それ自体が独立した規模のソフトウェア工学作業であること、の3点から**本プロジェクトの
  スコープ外**と結論した（2026-08-19、ユーザーと協議のうえ決定）。

## この実験で実証できたこと

**「言語仕様として書いた決定論・観測可能性が、自作の CI を離れた現実的なワークロードでも、
そのとおりに機能する」** ということです。これがこの実験が持つ、最も重要な検証結果です。

具体的には、次の3点が示されています。

1. **決定論はニューラルネットワークの学習という非決定性の温床になりやすい領域でも保たれる。**
   浮動小数点演算・確率的初期化・勾配計算を伴う学習ループにおいて、同一 seed からの
   2回の学習が bit-for-bit で一致するチェックポイントを生成することを確認した。これは
   ReasonScript の`goal → derive → prove → apply → converge → rollback` という状態遷移
   意味論が、机上の言語設計にとどまらず、実際のワークロードで決定論を担保できることの
   実証である。
2. **観測は計算に副作用を持たない、という設計が実測で裏付けられた。**
   活性・勾配などの中間値をエクスポートする観測層を入れても最終出力が変わらないことを
   確認しており、「検証のためのログ出力が結果を変えてしまう」という観測系にありがちな
   問題を回避できていることを示している。
3. **独立実装による相互検証という設計が機能する。**
   Python 側の実装から独立した Rust の検証ツールが、チェックサムとダイジェストの両方で
   一致する値を算出したことは、ReasonScript の成果物（`.rstensor` 等）が単一実装の
   自己申告ではなく、第三者実装によって再計算・検証可能な形式になっていることを示している。

同時に、この実験は ReasonScript の**限界も可視化した**。11件の制約・不具合の発見（うち3件を
修正）と、木構造インタプリタゆえの性能特性（関数呼び出しを伴う複雑な計算では、単純ループ比で
約13倍のオーバーヘッドが生じる）は、「決定論と検証可能性を仕様で保証する」設計が、
**実行速度とのトレードオフの上に成り立っている**ことを定量的に示している。

以上のとおり、ReasonScript の中核仕様（決定論・観測可能性・独立検証可能性）は肯定的に
実証された一方、Model A〜D の構造的優位性そのもの（Reason Relation Matrix や疎ルーティングが
学習効率を実際に改善するか）は、フルマトリクスが未実施であるため**まだ検証されていない**。
この区別を曖昧にしないことが、本レポートの方針です。
