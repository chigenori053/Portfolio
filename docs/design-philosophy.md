# 設計思想 — 5つの原則

6つのプロジェクトは題材も言語もばらばらですが、通底する原則は共通しています。
ここではその原則と、各プロジェクトでの具体的な実装を対応付けます。

---

## 原則1 — 決定論と再現性を、仕様で保証する

### 主張

「同じ入力からは同じ結果が出る」を、努力目標や運用ルールではなく、
**言語仕様・スキーマ・検証ゲート**として実装する。

### 実装

**ReasonScript** は、決定論をコンパイルパイプラインそのものに組み込んでいます。

```
.rsn → Surface AST → Semantic AST → Reason IR → ExecutionPlan → InferenceResult
```

同一入力からは必ず同一の `ExecutionPlan` と `InferenceResult` が生成されます。
Reason IR は JSON Schema で機械的に検証され、`./reason ci` が1,116件のテストで
パイプライン全体を守っています（実行確認済み: 2026-08-12 / commit `0efb2ab`）。

**Design_BrainModel** は、決定論の実現手段まで仕様で凍結しています。

| 項目 | 固定値 |
|---|---|
| ハッシュアルゴリズム | FNV-1a 64bit |
| シード | `0xcbf29ce484222325` |
| 素数 | `0x100000001b3` |
| 浮動小数点の整形 | `{:.6}` の固定精度文字列 |
| リスト型フィールド | ハッシュ前にソート |
| `Option` の符号化 | `null` または `some:<value>` |
| 空文字列と `None` | **区別する** |
| テンプレート選択の曖昧性閾値 | `TEMPLATE_SELECTION_EPSILON = 1e-6` |

決定論ゲートは、同一入力に対して `snapshot_v2` ハッシュ・テンプレート選択・説明テキストが
完全一致することを要求します。

**LanguageModel** は、非決定性が残る場合の扱いまで規定しています。

> 同一のモデル、ベクトル辞書、メモリスナップショット、検索設定、乱数 seed、入力に対する
> 候補順位と検証結果は再現可能でなければならない。
> GPU 等による非決定性が残る場合は、**その範囲と許容差を記録する**。

### なぜこれが重要か

再現できないものは、検証できません。検証できないものは、責任を持って使えません。
AIを安全性・監査・規制が関わる領域で使おうとするなら、決定論は前提条件になります。

## 原則2 — 「記憶」と「真実」を分離する（Truth Boundary）

### 主張

連想記憶は**候補を出すだけ**であり、事実を確定してはならない。
「意味的に近い」と「その関係が成立する」は、厳密に別のことである。

### 実装

**LanguageModel** が最も明快に定式化しています。

> HolographicMemory は **Semantic Activation Field** であり、真実の保存先ではない。
> ベクトル類似度、復号結果、ニューラルモデルの確信度だけを根拠として Relation を断定してはならない。
> — *MRA Holographic Semantic Language Model 仕様書 v0.1, §2.1*

三層が論理的にも永続化上も分離されます。

| 層 | 正規性 |
|---|---|
| Semantic Space | 非正規 |
| HolographicMemory | 非正規・**再構築可能** |
| MRA Molecular Memory | **正規** |

そして「HolographicMemory の削除・再構築によって正規知識が失われてはならない」——
連想記憶は捨てて作り直せるキャッシュとして位置づけられています。

**COHERENT**（推論モデル: **BrainModel**）では、同じ構図が「Recall-First」として現れます。
HolographicMemory（System 1）が Resonance によって候補を想起し、
ReasoningAgent と ValidationEngine（System 2）が検証して確定します。

この分離は理念だけでなく**実装に直結しています。** `MemorySpace` は
`AcceptStore` / `ReviewStore` / `RejectStore` の三領域を持ち、
判定結果には必ず根拠ログ（`DecisionLog`）が添えられます。

「記憶があれば想起し、なければ初めて推論する」という運用も実装されていますが、
**その効果はまだ測定されていません。**（[検証状況](projects/coherent.md#検証結果と証拠の強さ)）

**VisionWorldModel** では対象が視覚に変わります。
**観測された VisualAtom** と **推論された World 構成要素** が分離して保持されます。

| プロジェクト | 候補を出す側 | 確定する側 |
|---|---|---|
| LanguageModel | HolographicMemory | Molecular Memory + Evidence 検証 |
| COHERENT / BrainModel | HolographicMemory（Dynamic / Static / Causal） | ReasoningAgent + ValidationEngine（Accept / Review / Reject） |
| VisionWorldModel | 観測（VisualAtom） | 推論（World components）+ Decision |
| Design_BrainModel v2 | システム構造から**想起**されたコード | 設計意図とその検証 |

Design_BrainModel が「コードを生成する」ではなく **「コードを想起する」**と表現しているのは、
この原則に従っているためです。想起されたコードは候補でしかなく、
それが正しいかを決めるのは上位にある設計意図です。

### なぜこれが重要か

現在のRAGやベクトル検索ベースのシステムは、**類似度をそのまま知識として扱ってしまいます。**
`Alice` と `Book` のベクトルが近いことは、`Alice --likes--> Book` の根拠にはなりません。
この境界を守らないかぎり、幻覚は原理的に排除できません。

## 原則3 — 判断しないことを、正当な出力にする

### 主張

根拠が不十分なとき、**保留する・棄権する**ことが正常な振る舞いである。
無理に答えを出すことのほうが異常である。

### 実装

**VisionWorldModel** は判断を4値で返します。

| 判断 | 意味 |
|---|---|
| `ACCEPT` | 根拠十分。受理 |
| `REVISE` | 修正して再検討 |
| `DEFER` | **保留** |
| `ABSTAIN` | **棄権** |

さらに `src/adaptive_abstention.rsn` として、棄権の判断が**独立したモジュール**になっています。
`adaptive_reversibility.rsn`（可逆性評価）と並んでいることも示唆的で、
「戻せるか」「やらないでおくか」が推論の一級要素として扱われています。

Phase 3A の推論タスクも `CLASS_A` / `CLASS_B` / **`UNDETERMINED`** の三値です。

**LanguageModel** では、Audit Logger が**棄却理由**まで記録します。
「答えなかった」ことも監査対象になっています。

### なぜこれが重要か

LLMは根拠が薄くても何らかの答えを返します。それが有用な場面もありますが、
判断の帰結が重い領域では**「わからない」と言える能力**のほうが価値を持ちます。

## 原則4 — 仕様書を先に書き、Phase で刻む

### 主張

実装は仕様を上書きしてはならない。進捗は、検証可能な単位に刻んで積み上げる。

### 実装

**規範語の徹底** — MUST / MUST NOT / SHOULD / MAY を明示的に定義してから仕様を書く。

**スコープの明示** — LanguageModel の仕様書には「v0.1 の非対象」という節があり、
やらないことが列挙されています。スコープクリープを設計段階で止める仕掛けです。

**Phase 分割** — VisionWorldModel の刻み方が典型です。

```
Phase 1     分子構造の固定表現
Phase 2     状態遷移
Phase 3A    状態 → 推論のマッピング
Phase 3B-1  結合状態の遷移
Phase 3B-2  結合型の遷移とバージョニング
Phase 3B-3  結合の形成と解離
Phase 3C-1  分子の分割と結合
            → 複数分子の相互作用 → 適応的構造推論
```

**各Phaseが必ず持つもの：**
検証コマンド · pytest テスト · 機械可読な成果物（JSON） · 人間可読レポート

**仕様の凍結** — ReasonScript の `Semantic Language Core v0.2` は 2026-06-15 に凍結。
Design_BrainModel は PhaseA-Final で V2 API を既定に昇格し、
非推奨APIに `since` と `note = "Will be removed in PhaseC"` を付与しています。

**不正なショートカットの禁止** — VisionWorldModel Phase 3A の記述が象徴的です。

> 判断は Phase 2 の状態トレースから、バージョン付きの evidence 抽出と ReasonScript の
> readout ルールを通じて導出される。**フィクスチャ名や入力IDによる参照は一切使わない。**

テストを通すための「答えの先読み」を、構造的に禁止しています。

### なぜこれが重要か

AIエージェントを使った開発では、コードは高速に増えます。
仕様が後追いになった瞬間、**何が正しいのかを判定する基準そのものが失われます。**

## 原則5 — AIとの協働そのものを、設計対象にする

### 主張

AIエージェントは「便利な道具」ではなく、**権限と責務を定義すべきチームメンバー**である。

### 実装

**Design_BrainModel の Agent Operational Charter** が最も踏み込んでいます。

権限階層：

```
1. specs/
2. Rule.md
3. TASK_STATE.yaml
4. 実装コード

→ 実装が仕様を上書きしてはならない
```

役割分担：

| 役割 | 担当 | できること | できないこと |
|---|---|---|---|
| Architect | 人間 | 仕様承認、対立の解決、最終決定 | — |
| ResearchAgent | Gemini CLI | 仕様案生成、代替設計 | **本番コードを書かない** |
| CodingAgent | Codex CLI | 承認済み仕様の実装、テスト生成 | **アーキテクチャを再定義しない** |
| ValidationAgent | — | 仕様と実装の整合検証、回帰チェック | — |

**複数のAIを、能力ではなく権限で分離している**点が重要です。
提案する者と実装する者を分けることで、AIが自分の提案を自分で正当化する経路を断っています。

**DBM 全体の位置づけ**も同じ思想の延長にあります。

> *"DBM doesn't compete with Claude Code — it provides the structure and safety that Claude Code tends to lack."*

コード生成をAIに任せる前提を受け入れたうえで、
**設計意図の保持・実行安全性・構造整合性を担う層を別に作る**という戦略です。

各リポジトリの `AGENT.md` / `AGENTS.md` / `Rule.md` も同じ役割を果たしています。

### なぜこれが重要か

AIエージェントの能力が上がるほど、ボトルネックは「生成できるか」ではなく
**「生成されたものが正しいと、どうやって言えるか」**に移ります。
その判定機構を人間の注意力に依存させないための、構造的な答えです。

## 原則どうしの関係

5つの原則は独立しておらず、互いを支えています。

```
        原則4「仕様を先に書く」
                │
                │ が、判定基準を与える
                ▼
        原則1「決定論を仕様で保証」
                │
                │ が、検証を可能にする
                ▼
   原則2「記憶と真実の分離」 ──┬── 原則3「判断しない選択肢」
   何が事実かを構造で守る      │    確定できないときの逃げ道
                              │
                              ▼
        原則5「AI協働の統制設計」
        以上すべてを、AIを含むチームで維持する仕組み
```

出発点は **「AIの出力を、人間が事後に検査・再現・巻き戻しできるようにする」** という一点です。
そこから、言語処理系（ReasonScript）、制御レイヤー（Design_BrainModel）、
記憶アーキテクチャ（COHERENT / BrainModel、LanguageModel）、世界モデル（VisionWorldModel）が
それぞれの角度で導かれています。

## トレードオフの自覚

この設計方針にはコストがあります。

| 得るもの | 支払うもの |
|---|---|
| 検証可能性・監査可能性 | 仕様書77本、CI テスト1,116件という開発コスト |
| 再現性 | 非決定的な最適化・GPU並列の一部を諦める |
| 幻覚の構造的排除 | 連想だけで即答する速さを捨てる |
| 設計整合性の維持 | エージェントに自由に書かせる速度を制限する |

**このコストが正当化されるのは、間違いの代償が大きい領域**——安全性、規制対応、監査、
インフラ、医療、金融といった文脈です。逆に、素早い試作や創造的な生成が目的なら、
この方針は過剰になります。

その線引きを自覚したうえで、あえて「重い側」を選んでいるのが、この一連のプロジェクトの立場です。
