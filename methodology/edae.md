# Evidence-Driven Architecture Engineering(EDAE)

## 定義

**Evidence-Driven Architecture Engineering(EDAE)** は、本ポートフォリオの全プロジェクトを貫く開発方法を指すために本書で用いる呼称である。「仕様を先に固定し、実装の主張には必ず検証可能な証拠を対応付け、証拠の強さが不十分な主張は成果として扱わない」という進め方を指す。

以下5つの原則で構成される。

## 原則1 — 決定論と再現性を、仕様で保証する

「同じ入力からは同じ結果が出る」を、努力目標や運用ルールではなく、**言語仕様・スキーマ・検証ゲート**として実装する。

ReasonScript は決定論をコンパイルパイプラインそのものに組み込み(`.rsn → Surface AST → Semantic AST → Reason IR → ExecutionPlan → InferenceResult`)、Design_BrainModel は決定論の実現手段(ハッシュアルゴリズム、シード、浮動小数点整形精度)まで仕様に凍結している。再現できないものは検証できず、検証できないものは責任を持って使えない、という立場に基づく。詳細: [決定論的推論ケーススタディ](../case-studies/deterministic_reasoning.md)。

## 原則2 — 「記憶」と「真実」を分離する(Truth Boundary)

連想記憶は候補を出すだけであり、事実を確定してはならない。「意味的に近い」と「その関係が成立する」は厳密に別のことである。

> HolographicMemory は Semantic Activation Field であり、真実の保存先ではない。ベクトル類似度・復号結果・ニューラルモデルの確信度だけを根拠として関係を断定してはならない。
> — MRA Holographic Semantic Language Model 仕様書 v0.1, §2.1

現在のRAGやベクトル検索ベースのシステムは、類似度をそのまま知識として扱ってしまう傾向がある。この境界を守らない限り、幻覚は原理的に排除できない、という診断に基づく設計。詳細: [MRA](../projects/mra.md)。

## 原則3 — 判断しないことを、正当な出力にする

根拠が不十分なとき、保留する・棄権することが正常な振る舞いである。無理に答えを出すことのほうが異常である。

VisionWorldModel は判断を `ACCEPT`/`REVISE`/`DEFER`/`ABSTAIN` の4値で返す。LLMは根拠が薄くても何らかの答えを返すが、判断の帰結が重い領域では「わからない」と言える能力のほうが価値を持つ、という立場。

## 原則4 — 仕様書を先に書き、Phaseで刻む

実装は仕様を上書きしてはならない。進捗は、検証可能な単位に刻んで積み上げる。

MUST/MUST NOT/SHOULD/MAYの規範語を明示的に定義してから仕様を書き、Phase 0→1→2→3A→3B-1→3B-2→3B-3→3C-1のように細かく刻んで進める。各Phaseは検証コマンドと機械可読な成果物(JSON)を必ず伴う。AIエージェントを使った開発ではコードが高速に増えるため、仕様が後追いになった瞬間、何が正しいかを判定する基準そのものが失われる、という認識に基づく。

## 原則5 — AIとの協働そのものを、設計対象にする

AIエージェントは「便利な道具」ではなく、権限と責務を定義すべきチームメンバーである。

Design_BrainModel の Agent Operational Charter(`AGENT.md`)は、Architect(人間)/ResearchAgent/CodingAgent/ValidationAgentという役割分担と、`specs/ > Rule.md > TASK_STATE.yaml > 実装コード` という権限階層を定義している。複数のAIを能力ではなく権限で分離することで、AIが自分の提案を自分で正当化する経路を断っている。実践方法の詳細は[AI支援開発の責任分界](ai_assisted_development.md)を参照。

## 原則どうしの関係

```
        原則4「仕様を先に書く」
                │ が、判定基準を与える
                ▼
        原則1「決定論を仕様で保証」
                │ が、検証を可能にする
                ▼
   原則2「記憶と真実の分離」 ──┬── 原則3「判断しない選択肢」
   何が事実かを構造で守る      │    確定できないときの逃げ道
                              ▼
        原則5「AI協働の統制設計」
        以上すべてを、AIを含むチームで維持する仕組み
```

出発点は「AIの出力を、人間が事後に検査・再現・巻き戻しできるようにする」という一点であり、そこから言語処理系(ReasonScript)、制御レイヤー(Design_BrainModel)、記憶アーキテクチャ(COHERENT/LanguageModel)、世界モデル(VisionWorldModel)がそれぞれの角度で導かれている。

## トレードオフの自覚

この設計方針にはコストがある。

| 得るもの | 支払うもの |
|---|---|
| 検証可能性・監査可能性 | 仕様書77本(ReasonScript)、CIテスト1,116件という開発コスト |
| 再現性 | 非決定的な最適化・GPU並列の一部を諦める |
| 幻覚の構造的排除 | 連想だけで即答する速さを捨てる |
| 設計整合性の維持 | エージェントに自由に書かせる速度を制限する |

このコストが正当化されるのは、間違いの代償が大きい領域——安全性、規制対応、監査、インフラ、医療、金融といった文脈である。逆に、素早い試作や創造的な生成が目的なら、この方針は過剰になる。その線引きを自覚したうえで、あえて「重い側」を選んでいるのが、この一連のプロジェクト群の立場である。
