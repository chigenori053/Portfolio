# Test Strategy — テスト戦略

## 方針

「テスト数が多い」ことではなく、**各テストが何を保証するか**を明示することを優先する。テスト総数の単純合計は、プロジェクトによって粒度が異なり比較にならないため、本ポートフォリオでは中心指標として扱わない(詳細は[Verification Matrix](verification_matrix.md)を参照)。

## 仕様駆動のテスト設計

全プロジェクトで、実装に先立って仕様書を書く方針を採用している。

- **規範語の徹底** — MUST / MUST NOT / SHOULD / MAY を明示的に定義してから仕様を書く(例: LanguageModel の Truth Boundary)
- **スコープの明示** — 「v0.1 の非対象」のように、やらないことを列挙してスコープクリープを設計段階で止める(LanguageModel 仕様書)
- **Phase 分割** — 検証可能な単位に刻んで進める。各Phaseは検証コマンド・テスト・機械可読な成果物(JSON)・人間可読レポートを必ず伴う(VisionWorldModel: Phase 1 → 2 → 3A → 3B-1 → 3B-2 → 3B-3 → 3C-1)

## 不正なショートカットの禁止

検証系を自作する際に最も起きやすい自己欺瞞は、「テストを通すための答えの先読み」である。VisionWorldModel Phase 3A ではこれを構造的に禁止している。

> 判断は Phase 2 の状態トレースから、バージョン付きの evidence 抽出と ReasonScript の readout ルールを通じて導出される。フィクスチャ名や入力IDによる参照は一切使わない。

## プロジェクト別のテスト構成

| プロジェクト | テスト形態 | 規模 |
|---|---|---|
| ReasonScript | CI パイプライン(チェックアウト→ワークスペース検証→診断→アーティファクト→Goldenコーパス→エージェントプロトコル→DTO互換性→テストスイート) + Conformanceフレームワーク | テスト239ファイル、CI 1,116件パス(実行確認済み) |
| VisionWorldModel | Phase単位のpytest + 検証スクリプト + JSON成果物 | テスト14ファイル |
| Design_BrainModel | 決定論ゲート(ハッシュ完全一致の要求)+ Phase 6/7/8の機械可読レポート | ドキュメント55本 |
| COHERENT | Phase単位の実験レポート(PHASE0〜PHASE_C) + pytest | テスト30ファイル、実験レポート約20本 |
| mathlang | パーサ・評価器の意味論テスト(pytest) | テスト30ファイル |

## 決定論ゲート — テストで「たまたま一致」を排除する

Design_BrainModel は、ハッシュアルゴリズム(FNV-1a 64bit)・シード・浮動小数点の文字列化精度(`{:.6}`)・リストのソート・`Option`の符号化・空文字列と`None`の区別まで仕様に明記している。実装者の裁量が入る余地を潰すことで、「たまたま今は一致している」状態のテストパスを排除している。

## Golden Test

ReasonScript は `golden/` コーパスにより、ソースコードから中間表現への変換結果を期待値と比較する。コンパイルパイプラインの変更が既存の意味論を壊していないかを機械的に検証する。
